# Axe PARA — PARA — Parallélisme et travail hors du fil principal (METAL 673d6b2, Point de rupture HEAD 5ac0066, FERRO 248043a)

Origine : second tour. Contre-vérifié.

Références de lignes : METAL 0.8.0 (commit 673d6b2). « FERRO » désigne les modules moteur de METAL.

## Résumé

Axe PARA. Rien n'a été écrit dans les dépôts (METAL : git status vide, HEAD 673d6b2 ; Point de rupture : arbre identique à HEAD 5ac0066 au moment de la lecture). Tout est dans bancs/para/. Aucun serveur, aucun port, aucun paquet.

À signaler : le dossier ~/Projects/ferro, lu à 18 h 33 (commit 248043a, src = audio.js, motion.js, music.js, options.js, renderer.js), n'existait plus à 19 h 00 (date de modification de ~/Projects : 18 h 35). Je n'y ai rien écrit ; une autre session l'a sans doute déplacé. Il reste une copie de son renderer dans scratchpad/ferro_renderer_248043a.js.

Méthode. La machine était très chargée (charge moyenne de 27 à 180). Sur une même série, le pas de simulation vaut 0,90 ms en temps CPU et 9,6 ms en temps d'horloge (p99 182 ms) : l'horloge est inutilisable. J'ai donc mesuré en temps CPU par fil (process.threadCpuUsage de Node 24), dans le domaine principal de chaque fil, et j'ai vérifié l'égalité des états par empreinte. Les mesures de latence viennent de Chrome 157 sans interface, sur une page file:// où la vraie simulation de METAL tourne dans un worker créé depuis un Blob.

Ce que j'ai trouvé.
1) Point de rupture a déjà l'architecture complète : hôte (hote.js), worker (sim/travailleur.js), protocole (sim/protocole.js), repli sur le fil principal, page unique avec le worker en Blob sans dupliquer le code, tests. C'est récoltable dans FERRO presque tel quel. Ses limites pour un FPS : horloge par setTimeout (cadence mesurée à 20 ms au lieu de 16,7 dans un worker Chrome), interpolation calée sur l'heure d'arrivée avec un tick de retard, pas de reprise après panne, pas de pause de la démo en arrière-plan.
2) Déplacer FSimulation dans un worker est faisable et l'état reste identique : mêmes empreintes sur 2 scénarios de 1 800 pas, et même position finale dans Chrome. Le coût de simulation sur le fil principal passe de 0,52–0,78 ms à 0,11–0,13 ms par image (−79 à −84 %) et son maximum de 30–39 ms à 1,4–2,6 ms. Mais le format du paquet décide de tout : cloner l'état en objets coûte 0,92–1,08 ms par image sur le fil principal, soit plus que la simulation elle-même. Un Float64Array empaqueté et transféré coûte 0,11–0,13 ms et donne un miroir identique bit à bit (0 valeur différente sur 3 076).
3) Le worker ne supprime pas les pointes, il les sort de l'image : l'image n'est plus perdue, l'état du monde arrive un tick plus tard. Dans Chrome, sur 1 800 images, une seule a reçu son état en retard, malgré 8 pas de plus de 4 ms dont un de 19,5 ms. Il faut donc d'abord corriger les causes (IA-01, SIM-01 à 06), puis déplacer.
4) Latence : le lacet et le tangage ne sont écrits qu'à simulation.js:1909 par addition, donc la page peut les prédire exactement, sans latence ajoutée à la souris. L'aller-retour page → worker → page avec le pas réel vaut 0,6 ms en médiane (≤ 2 ms dans 97,9 % des cas) : on peut dessiner à l'arrivée de l'état, dans la même image.
5) Travaux faciles à sortir, par ordre de rentabilité : synthèse des sons (303 ms CPU, lot maximal de 58 ms, ramenés à 1,5 ms au total sur le fil principal) et musique (85–89 ms ramenés à 0,06 ms) ; génération du monde et FSimulation.create (143–208 ms CPU ramenés à 0,07 ms avec des maillages empaquetés, ou 17–22 ms si l'on clone le monde) ; points de reprise (2,5–9,2 ms ramenés à 0,05–0,07 ms).
6) Contraintes vérifiées dans Chrome 157 en file:// : worker classique depuis un Blob accepté, worker en module refusé, SharedArrayBuffer absent, AudioWorklet refusé depuis un Blob mais accepté depuis une URL data:, OffscreenCanvas avec WebGL2 dans un worker accepté. Safari et Firefox restent à vérifier.
7) Démo qui dure : enchaîner 9 mondes dans un même worker ne fait pas grossir la mémoire (25 à 29 Mo vivants, +0,1 Mo au plus par cycle de 3 mondes). Avec des ticks cadencés par les images de la page, la démo s'arrête d'elle-même quand l'onglet est caché.

Plan proposé, du plus rentable au plus risqué : module FERRO (hôte, worker de tâches, protocole) ; audio en tâche ; génération en tâche ; simulation dans le worker en mode « image suivante » avec caméra prédite ; dessin à l'arrivée et démo ; préparation du rendu dans le worker et SharedArrayBuffer en option. Le rendu complet dans un worker (OffscreenCanvas) n'est pas recommandé maintenant.

## Constats

### PARA-01 — Point de rupture a déjà l'hôte, le worker et le protocole : à récolter dans FERRO, avec six limites à corriger pour un FPS
- sévérité haute · catégorie architecture · effort M · gain qualitatif
- contre-vérification : **confirmé**, priorité P1 · qualité sans objet · moteur (dans METAL)
- lieux : point-de-rupture/Jeu/src/hote.js:46-116; point-de-rupture/Jeu/src/sim/travailleur.js:29-167; point-de-rupture/Jeu/src/sim/protocole.js:1-60; point-de-rupture/Jeu/src/foule.js:763-812; point-de-rupture/Jeu/src/jeu.js:102-175; point-de-rupture/Jeu/construire.py:27-58; point-de-rupture/Jeu/src/interface/titre.js:675-678; point-de-rupture/Jeu/verifications/hote.test.mjs

**Preuve.** Lecture de Point de rupture (HEAD 5ac0066). Oui, la simulation tourne dans un Web Worker. hote.js:96-116 : le worker est construit depuis un Blob qui concatène le texte des scripts marqués data-travailleur ; construire.py:27-56 donne à chaque module un rôle (page, partage, simulation) et pose les scripts de simulation en type="text/plain", donc sans dupliquer le code dans la page. Repli : hote.js:46-61 exécute ces scripts dans la page et appelle PDR.travailleur.creer ; les messages passent par queueMicrotask (hote.js:66-72) ; les messages partis avant « pret » sont rejoués (hote.js:77). Worker : travailleur.js:29 (20 itérations/s, rattrapage 4, abandon au-delà de 10, réserve de 4 tampons), boucle par setTimeout (110-125), tampon d'unités transféré puis rendu par la page (71-96, 141-143 ; jeu.js:172). Page : foule.js:763-772 garde deux états et lisse l'intervalle d'arrivée (0,25, borné 8–250 ms), foule.js:807-812 en tire alpha. Tests : verifications/hote.test.mjs (worker, worker refusé, pas de Worker) et sim.test.mjs:382-470 (horloge factice). Taille : hote.js 6 138, travailleur.js 8 530, protocole.js 12 156 octets. Limites : (a) setTimeout(16,7) dans un worker Chrome 157 donne p50 20,0 ms (chrome/caps.html) : bon à 20 Hz, pas à 60 ; (b) l'interpolation suit l'heure d'arrivée, pas le numéro d'itération : un tick de retard (50 ms) et arrêt sur image si un état tarde ; (c) allocations à chaque état : monde.js:1688 ev.slice, objets eco et lieux, copies de voile, minicarte et combats non recyclées ; (d) panne après « pret » = partie perdue (jeu.js:124-127) ; (e) titre.js:675-678 ne met en pause que l'écran « partie » : en démo, onglet caché, le worker continue (lu dans le code, minuteries d'arrière-plan à vérifier) ; (f) en repli, boucle() peut enchaîner 4 itérations dans une même tâche du fil principal (travailleur.js:117).

**Cause.** Le module a été écrit pour un RTS à 20 Hz et vit dans le jeu, pas dans le moteur. METAL et BITUME n'ont aucun worker (aucune occurrence de Worker dans leurs sources).

**Proposition.** Créer dans FERRO src/host.js à partir de hote.js, presque tel quel : FHost.create({onMessage, onCrash, selector:'script[data-worker]', forceMain, name}) rend {mode:'worker'|'main', reason, post(msg, transfer), request(type, payload, transfer) → Promise, dispose()}. Garder : Blob classique, repli complet avec le même code de worker, livraison par microtâche, rejeu des messages d'avant « ready ». Ajouter : (1) request/réponse avec identifiant pour les tâches ponctuelles ; (2) un chien de garde (ping chaque seconde, onCrash après 3 s sans réponse) ; (3) la recette de build par rôles, à reprendre dans tools/build.py des jeux ; (4) deux cadences au choix dans le worker : « libre » (celle de Point de rupture, pour un RTS) et « image » (un message d'entrée par image de la page, pour un FPS, voir PARA-04) ; (5) numéro d'itération et durée de pas dans chaque état, pour interpoler sur le temps simulé ; (6) recyclage de tous les tampons transférés, pas seulement celui des unités. Point de rupture garde PDR.hote comme alias.

**Gain attendu.** Un seul module testé pour les trois jeux au lieu d'une copie par jeu. Environ 27 Ko de source déjà écrits et testés deviennent communs. Corrige au passage les limites (c) à (f) de Point de rupture.

**Risques.** Compatibilité FERRO : module nouveau, sans effet sur un jeu qui ne l'appelle pas. Point de rupture doit continuer à passer hote.test.mjs et sim.test.mjs avec l'alias. Les noms d'API de FERRO sont en anglais, ceux de Point de rupture en français : prévoir l'alias. Taille : +6 à 8 Ko par jeu.

**Vérifier par.** Porter verifications/hote.test.mjs dans FERRO (3 cas existants) et ajouter : request/réponse, chien de garde avec horloge factice, tampons tous rendus (0 allocation après 100 états). Point de rupture : sa suite complète reste verte avec l'alias.

**Contre-vérification.** Code relu ligne par ligne : hote.js:46-61 (repli sur le fil), 66-72 (queueMicrotask), 96-116 (Blob classique, onerror avant « pret » = repli), travailleur.js:29 et 110-125 (minuterie, rattrapage 4, abandon au-delà de 10), foule.js:763-772 et 807-812 (alpha calé sur l'heure d'arrivée), jeu.js:102-127 (un hôte neuf par partie, panne = arrêt), titre.js:50, 216-230, 675-678 (pause seulement pour l'écran « partie »). Tailles exactes (6 138, 8 530, 12 156 octets). Arbre de travail propre au moment de ma lecture. Deux réserves. (a) Le chien de garde proposé (ping chaque seconde, panne après 3 s) doit être suspendu quand document.hidden : les minuteries d'un onglet caché sont ralenties par le navigateur et déclencheraient de fausses pannes. (b) Un worker neuf par partie repart à froid (voir PARA-V3 : 16 à 20 ms de démarrage, premiers pas 2 à 3,5 fois plus lents) : ajouter un message de réinitialisation plutôt que de recréer. La cadence « image » ne doit pas promettre l'absence de latence (voir PARA-05 et PARA-V1).

### PARA-02 — Couplage page ↔ simulation de METAL : 229 chemins lus, 5 appels synchrones et 2 écritures à transformer en protocole
- sévérité haute · catégorie architecture · effort M · gain mesuré
- contre-vérification : **confirmé**, priorité P2 · qualité sans objet · jeu
- lieux : src/game.js:141; src/game.js:193-237; src/game.js:256; src/game.js:290; src/game.js:418-586; src/game.js:587-674; src/game.js:675-722; src/soundscape.js:26-40; src/simulation.js:2219

**Preuve.** census.mjs fait tourner le vrai game.js (harnais LOOP) avec un proxy enregistreur à la place de sim.state côté page : 1 200 images, monde de campagne 9. Par image, la page lit 706 nombres en médiane (max 1 043), 126 chaînes (738 octets) et 222 booléens, sur 229 chemins. Racines les plus lourdes : enemies (22 champs lus sur environ 90 par ennemi), pickups, debris, pipes, traps, lifts, doors, mechanisms. Appels synchrones vers la simulation : sim.destruction 117 829 fois (98 par image : isAlive à game.js:256, game.js:290 et soundscape.js:40), sim.ray 178 fois (soundscape.js:27), sim.nearestInteraction à chaque rafraîchissement du HUD (game.js:651), sim.stats (game.js:589), sim.ground pour les marqueurs d'attaque (game.js:445). Écritures de la page dans l'état : sim.state.events.length=0 (game.js:236) et sim.state.weapon (game.js:141, 738). Commandes : selectWeapon, selectLeftWeapon, buy, shopOffers, setDifficulty, restore, snapshot, exportLoadout (simulation.js:2219). L'état contient aussi le monde entier (state.world) : 3,5 Mo sérialisés.

**Cause.** La page et la simulation partagent le même objet d'état et s'appellent directement. Rien ne sépare l'état de rendu (environ 1 000 scalaires) de l'état interne (chemins, mémoire des ennemis, navigation).

**Proposition.** Écrire src/simview.js : la liste déclarative des champs que la page a le droit de lire (scalaires et listes, comme bench/para/schema.mjs), plus quatre remplacements. (1) isAlive : un Uint8Array « vivant » par identifiant destructible, renvoyé à chaque révision de destruction. (2) Occlusion sonore : exécuter FSoundscape.sample du côté de la simulation et publier ses 8 valeurs. (3) HUD : nearestInteraction et stats publiés toutes les 0,09 s. (4) Marqueurs d'attaque : la simulation publie les 3 hauteurs de sol par ennemi en préparation à moins de 24 m. Les écritures deviennent des commandes : {t:'weapon', slot}, et les événements sont livrés avec l'état au lieu d'être vidés par la page. Faire d'abord ce travail sur le fil principal : la page ne lit plus que la vue, la simulation reste où elle est. Le passage en worker (PARA-04) devient alors un changement de transport.

**Gain attendu.** Rend le déplacement en worker possible sans réécrire models(), FEffects ni FActors : la page lit un miroir aux mêmes noms de champs. Supprime aussi 98 appels isAlive par image.

**Risques.** Le recensement ne couvre que 20 s d'un monde : bullets, projectiles, bossAttacks, hazards et trophées y étaient vides. Le schéma doit être établi sur une campagne complète et un combat de boss. Sauvegardes : aucun effet, snapshot() ne change pas. ### PARA-V1 — Un dessin WebGL fait hors du rappel rAF n'est remis au compositeur qu'à l'image suivante : la simulation dans un worker coûte une image de latence au FPS
- sévérité haute · catégorie latence · effort S · gain mesuré
- ajouté par le contre-vérificateur (non recontrôlé) · qualité identique · moteur et jeu
- lieux : src/game.js:683-696; src/game.js:717-722; src/simulation.js:1902-1909; bench/para-verif/chrome/make.mjs

**Preuve.** Chrome 157 sans interface, page file:// (bancs/para-verif/chrome/verif.html, résultats dans verif.json). Canevas WebGL2 sans preserveDrawingBuffer : le tampon est effacé dès qu'il a été remis au compositeur, ce que readPixels détecte. 40 essais par cas. Dessin dans le rappel rAF : remis 1,1 ms après (p90 1,4 ms), 0 rAF d'écart. Dessin dans une tâche 1 ms après le rAF : remis 17,6 ms après ce rAF (16,6 ms après le dessin), 1 rAF d'écart dans 40 essais sur 40. Dessin 5 ms après : 17,6 ms. Dessin 10 ms après : 17,7 ms. Soit 120 essais sur 120 remis à l'image suivante. Or un message de worker n'est jamais lisible de façon synchrone (SharedArrayBuffer absent en file://), donc l'état calculé pour l'entrée de l'image N ne peut être dessiné qu'au rAF N+1. game.js:683-696 échantillonne aujourd'hui l'entrée et exécute sim.step dans le même rappel rAF que le dessin (game.js:722) : 0 image de retard.

**Cause.** Le navigateur ne compose le canevas qu'à l'étape de rendu qui suit les rappels rAF. Tout dessin fait dans une tâche ultérieure attend l'étape suivante, une période d'affichage plus tard.

**Proposition.** Inscrire la règle dans FERRO : FHost ne dessine jamais hors rAF, et le réglage latency:'arrival' de PARA-05 n'existe pas. Pour METAL, la simulation reste sur le fil principal par défaut (sim:'main'). Le mode sim:'worker' est une option, avec ce cycle : au rAF, la page applique le dernier état reçu, recale la visée (yaw de l'état du tick T plus la somme ordonnée des lookX envoyés après T, pour tenir compte du retour anticipé de simulation.js:1902), dessine, puis envoie l'entrée échantillonnée à la toute fin du rappel. L'overlay de diagnostic affiche « latence simulation : 1 image ». Si un jour la simulation doit quitter le fil principal sans latence, la seule voie est simulation et rendu dans le même worker avec OffscreenCanvas (PARA-09), l'entrée étant relayée en moins de 1 ms.

**Gain attendu.** Évite une régression de 16,7 ms (60 Hz) ou 8,3 ms (120 Hz) sur le déplacement, le tir et les impacts, et évite d'écrire le mécanisme d'échéance par minuterie, qui ne rapporte rien.

**Risques.** Mesure faite sur Chrome 157 sans interface sur macOS ; le comportement découle de la norme HTML (étape « update the rendering »), mais Safari et Firefox restent à contrôler avec la même page. Aucun effet sur le déterminisme, les sauvegardes ou la taille.

**Vérifier par.** Rejouer chrome/verif.html dans chaque navigateur cible : pour un dessin hors rAF, l'écart en rAF entre dessin et remise doit valoir 1. Test Node de la visée recalée : après 1 800 entrées dont une mort et un retour de checkPlayerBounds, la visée de la page est égale (Object.is) à celle de l'état.

### PARA-V2 — input.weapon est un écho de l'état renvoyé à chaque pas : avec un état en retard ou deux sous-pas, il annule un ramassage d'arme ; la boucle de sous-pas dépend aussi de events()
- sévérité haute · catégorie bug · effort S · gain mesuré
- ajouté par le contre-vérificateur (non recontrôlé) · qualité identique · jeu
- lieux : src/game.js:686; src/game.js:691-695; src/game.js:221; src/game.js:237; src/simulation.js:1908; src/simulation.js:611; src/simulation.js:593

**Preuve.** game.js:686 et 694 envoient input.weapon=selectedWeapon à chaque sous-pas ; game.js:237 recopie selectedWeapon=sim.state.weapon après chaque events() ; simulation.js:1908 appelle selectWeapon(input.weapon) à chaque pas ; simulation.js:611 et 593 sélectionnent l'arme ramassée. Essai (bench/para-verif/weapon-echo.mjs), ramassage émulé comme simulation.js:611 : legacy-s0, arme 0, ramassage de l'arme 1, puis un pas avec l'écho périmé weapon:0 → l'arme revient à 0 ; campaign-w10, arme 4, ramassage de l'arme 0, écho périmé 4 → retour à 4 ; avec l'écho à jour, l'arme ramassée reste. Sur le fil principal l'écho est toujours à jour ; dans un worker il est périmé dès qu'un état tarde d'un tick (2,1 % des cas mesurés par le premier agent) et à chaque image de 2 sous-pas (LOOP-05 : fréquent à 59,94 Hz). De plus game.js:691-695 exécute events() entre les sous-pas et quitte la boucle si le mode change (shopOpen à game.js:221, win, dead) : un worker qui enchaîne les sous-pas seul simule un pas de trop à l'ouverture d'une boutique. Le prototype du premier agent n'envoie jamais input.weapon et ne fait jamais 2 sous-pas : ces cas ne sont pas couverts par ses empreintes.

**Cause.** Le choix d'arme est transmis comme un niveau recopié depuis l'état, pas comme un ordre ponctuel ; et une partie de la logique de pas (arrêt des sous-pas) vit dans le code d'interface.

**Proposition.** À faire dès maintenant sur le fil principal, sans attendre un worker. (1) input.weapon n'est renseigné que sur l'image d'un geste du joueur (molette, touche, tactile), sinon undefined ; selectedWeapon devient une simple copie de sim.state.weapon pour l'affichage. (2) Exposer dans FSimulation une fonction stepFrame(dt, input) qui fait le découpage en sous-pas, remet à zéro les entrées ponctuelles après le premier, s'arrête après un sous-pas ayant émis shopOpen, win ou dead, et rend le nombre de sous-pas exécutés ; game.js appelle events() une fois après. (3) Dans le mode worker, c'est stepFrame qui tourne dans le worker.

**Gain attendu.** Supprime un bug certain du futur mode worker (arme ramassée aussitôt rangée) et rend le comportement identique entre fil principal et worker, sous-pas compris. Simplifie game.js:683-696.

**Risques.** Déterminisme : à prouver par rejeu, l'empreinte doit rester égale à celle d'aujourd'hui quand l'écho est à jour (c'est le cas dans les bancs, qui n'envoient pas input.weapon). events() regroupé en fin d'image change l'instant de quelques sons de 8 ms au plus dans les images à 2 sous-pas : à vérifier à l'oreille, ou garder events() entre les sous-pas sur le fil principal. Les tests de simulation qui passent input.weapon à chaque pas restent valides.

**Vérifier par.** Test de simulation : ramassage d'arme suivi de 3 pas sans input.weapon → l'arme ramassée reste ; même test avec stepFrame(1/30) (2 sous-pas). Rejeu de 4 scénarios de 1 800 pas : empreinte égale avant et après. Test du mode worker : état livré avec un tick de retard pendant un ramassage → arme conservée.

### PARA-V3 — Un worker neuf repart à froid : premiers pas 2 à 3,5 fois plus lents et pas maximal de 8 à 10 ms ; garder un seul worker par page et le chauffer au menu
- sévérité moyenne · catégorie saccade · effort S · gain mesuré
- ajouté par le contre-vérificateur (non recontrôlé) · qualité identique · moteur (dans METAL)
- lieux : point-de-rupture/Jeu/src/jeu.js:102-123; point-de-rupture/Jeu/src/hote.js:96-116; bench/para-verif/chrome/make.mjs

**Preuve.** Chrome 157 sans interface, page file://, 3 workers Blob neufs enchaînant 3 mondes chacun (bench/para-verif/chrome/verif.json). Démarrage du worker (analyse de 497 Ko de source) : 16 à 20 ms. Troisième monde dans le même worker : 94–111 ms, 44–51 ms, 45–58 ms dont 7–12 ms pour les 60 premiers, pas maximal 1,5–3,2 ms. Or PARA-12 propose de recréer le worker tous les 6 mondes, et Point de rupture en crée un par partie (jeu.js:102-123, hote.js:96-99).

**Cause.** Le code optimisé par le moteur JavaScript appartient à un isolat. Un worker neuf, ou la première exécution dans le worker d'un code déjà chaud sur la page, repasse par l'interpréteur.

**Proposition.** Dans FHost : un seul worker pour toute la vie de la page, créé au chargement, pendant le menu ; un message {t:'reset'} remet la simulation à zéro au lieu de terminate() ; terminate() est réservé à la panne détectée et à la fermeture. La démo, sur le fil principal ou dans le worker, chauffe naturellement le fil où elle tourne : ne pas la faire tourner dans un fil et le jeu dans l'autre. Point de rupture : réutiliser le worker entre deux parties via l'alias.

**Gain attendu.** Par changement de monde ou de partie : 16 à 20 ms de démarrage et environ 100 à 140 ms de calcul à froid évités ; pas maximal des premières secondes 8–10 ms → 1,5–3 ms ; 60 premiers pas 21–27 ms → 7–12 ms.

Les tests d'hôte de Point de rupture qui comptent les créations de worker sont à adapter. **Vérifier par.** Rejouer chrome/verif.html sur la page construite : le coût des 60 premiers pas d'une partie lancée après le menu doit rester sous 1,3 fois celui du troisième monde. Test d'hôte : deux parties de suite, un seul appel au constructeur Worker.
